## Changes from the plan, and why

- **Step 0's SDK diffs weren't empty.** The archives have `test/` directories (both commits) and three `README.md` files (base only) that the venvs don't install; no installed file differs. The run stopped and asked, Brian said continue, and the detail is in PROVENANCE.md.
- **The imported 1a runs were rerun**, since the venv that ran them was rebuilt afterwards and nothing records what SDK it imported.
- **Events:** 1,634 in `batch-bench`, not about 319,000; see PROVENANCE.md.
- **A wrong supersede, undone:** see NOTES.md.
- **wait_clean bulk-deletes unscheduled pods** now (`--field-selector spec.nodeName=`); see NOTES.md. Between-run cleanup only; no run measures it.
- **memdiag method** goes beyond the plan (gc.collect first, types counted before the snapshot, the first snapshot kept on disk, the probe's own frames dropped); see NOTES.md.
- **#42's new TCP connections** are 17–20 per run across both shells; the plan's summary said 18–19.
- **"Apiserver binds"** is the rule's label: it fired because max_in_flight was saturated below 90% of the target rate. That bound is in-flight slots times POST latency, so the client's cap and the apiserver's latency set it together.

## How the steps were driven

Each step ran `bench.py suite --only <prefixes>`, then `bench.py errored --supersede` (which moves a first errored attempt to `superseded/` with its reason in `superseded/WHY.md`), then the same suite again to rerun it once, then `bench.py errored` to flag any second failure. `bench.py candidate` rewrites `candidate.json` from the result files after Steps 2 and 3. Rerunning the same commands resumes where the files leave off:

```bash
# from the worktree root
export KUBECONFIG=$PWD/bin/KUBECONFIG
B=test/benchmarks/batch-claim; PY=$PWD/bin/bench-venv/bin/python
b() { "$PY" $B/bench.py "$@"; }
checked() { b suite --only "$@"; b errored --supersede; b suite --only "$@"; b errored; }
checked 1a-n1000 1a-n5000                                      # Step 0
checked 3s; b candidate                                        # Step 2
b candidate; checked 3a2; b candidate; checked 3a2; b candidate  # Step 3 (a second 3a2 pass runs a second winner, if the rule calls for one)
b candidate; checked 6v2a 6v2b 6v2c 6v2-baseline-pool1000      # Step 4 (includes the -hold20 entries, which run only after a starved run)
checked 6v2-memdiag 6v2-baseline-async                         # Step 5
checked 1d                                                     # Step 6
```
