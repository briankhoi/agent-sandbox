### Setup notes and deviations

- **Cluster.** One kind node, created from `kind-config.yaml`, not `make deploy-kind`. It uses deploy-kind's config plus kubelet `maxPods: 400`, a `/22` per-node pod CIDR (the default `/24` caps a node near 254 pods), and a mount of the repo at `/src` for the driver pod. The controller and sandboxd images were built and loaded with `dev/tools/push-images`, and deployed with `dev/tools/deploy-to-kube --extensions`, the two steps `deploy-kind` runs after creating the cluster.
- **deploy-kind's admission patch doesn't apply under kind v0.31.** `create-kind-cluster` patches `kubeadm.k8s.io/v1beta4`, but kind v0.31 renders `v1beta3`, so the patch matches nothing and is dropped without an error. In clusters made by `make deploy-kind` on this machine, the apiserver runs `--enable-admission-plugins=NodeRestriction` only, without `OwnerReferencesPermissionEnforcement`. This cluster's config uses `v1beta3`, so here the plugin is on, and the batch's ownerReferences are checked against the driver's Role.
- **Other kind clusters stopped.** Four other kind clusters on this machine were stopped for the whole benchmark, so they don't share the VM's CPU.
- **Node restart.** The VM restarted once between the earlier fill runs and this suite. All containers exited with 137 at the same moment, and the batch-bench node was started again. The imported 1a runs finished before that.
- **Driver location.** Scenarios 1, 2 and 5 drive from the macOS host through kind's port mapping, as the imported 1a runs did. Scenarios 3, 4 and 6 drive from a pod in the cluster (`batch-bench-driver/bench-driver`, `python:3.12-slim`), since the host can't reach pod IPs and this isn't Linux, so no host route is possible. Each row records where its driver ran.
- **Driver RBAC.** The driver pod runs under the README's batch driver Role, plus `get` on `agents.x-k8s.io` `sandboxes`. The README's Role lacks that rule, but the pod-IP connection mode and the baseline's `get_pod_name()` and `get_pod_ip()` read the Sandbox.
- **Base code.** Baselines run the SDK at `7fd162d9`, extracted with `git archive` into `bin/base-7fd162d` inside the mounted repo, so the driver pod can install it too. Each run records `sdk_file`, the path the SDK was imported from. Every venv installs the SDK as a copy in site-packages, never from the worktree.
- **Templates.** Every template sets `networkPolicyManagement: Unmanaged`. For the Ready templates this lets the in-cluster driver reach pod IPs. Scenario 5's per-group templates match scenario 1's, so the controller makes no NetworkPolicy per template.
- **Cleanup timing.** For the unschedulable runs (scenarios 1, 2 and 5), cleanup is timed until no claim of the run is left, with no cap, and the pods still present at that moment are counted. The remaining Pending pods are then force-deleted before the next run, since kind's garbage collector removes them at a few per second. For the Ready runs (3, 4 and 6), timing continues until the run's pods are gone.
- **410 re-list.** A 410 re-list can't be forced reliably on kind. It runs the same list and resync as `get_batch`, so the attach time stands in for it.
- **Imported runs.** `1a-n1000` runs 1–3 and `1a-n5000` runs 1–2 are imported from the earlier suite (defaults, pool 22, clean namespace). They predate client-side request counts, per-run cleanup timing and the RSS series, so those cells show `missing` for them.

- **The garbage collector's backlog after large unschedulable runs.** After scenario 2's N = 10,000 runs, kube-controller-manager's `garbage_collector_attempt_to_delete` queue held 11,642 items (read with `gc-queue.sh`). A Ready run's Sandboxes, owned by claims already deleted, waited behind them for over 20 minutes without being marked for deletion. That run (`4-batch-async-run2`, first attempt) was stopped before it wrote a result and was run again. From then on, the suite waits between runs until that queue holds fewer than 50 items. Runs before that check don't wait for it. In those, a Ready run's cleanup time can include this backlog when it comes right after scenario 1, 2 or 5. Scenarios 3 and 6 ran before any large unschedulable scenario, so they aren't affected.
- **A slow run right after scenario 2.** `4-batch-sync-run1` started at 02:21, right after scenario 2's last run (then at N = 5,000, see below). Its claims took about 10x longer to become Ready, and its pods about 9x longer to go, than every other cold N = 300 run in 3a, 3d and 4. The run's data-plane numbers (round latencies, Sandbox GETs, connections) match runs 2 and 3, so it counts for scenario 4, the only scenario that uses it. Its Ready and cleanup times aren't comparable with the others'. The likely cause is the cluster still processing scenario 2's cleanup; that wasn't measured. It isn't the backlog of about 319,000 Events the unschedulable runs left in `batch-bench`, since runs 2 and 3 were normal with those Events still present. The suite was stopped once during scenario 4 to check this, and the run it interrupted (`4-batch-async-run2`) left no objects behind and was run again.

- **Scenario 2 ran first at N = 5,000 by mistake.** The suite picks scenario 2's N (the largest N scenario 1 held) when it builds its plan. The first suite built its plan before 1a's N = 10,000 runs existed, so it fell back to 5,000. Scenario 1 held 10,000, so the `2b-n10000-*` and `2c-n10000-*` runs are the ones the addendum asks for. The `2b-n5000-*` and `2c-n5000-*` runs are kept as extra data.

- **Scenario 2 at N = 10,000 dropped detach and get_batch after its second run.** `2b-n10000-pool102-sync-run2` filled cleanly, then raised in `get_batch()` after `detach()` (see Problems). The crash left its Lease and claims behind, and they were deleted by hand. Its file keeps the fill-phase numbers and has no release numbers. Runs 1 and 2 of that variant detached and re-attached. Every later scenario 2 run goes straight from the fill to `release()`, since scenario 2 measures the fill.

### Problems found

- **The async driver's RSS grows during rolling acquire.** In 6c (async, 1,000 rollouts), the RSS samples rise several times over from start to end, while the sync batch (6a, 6b) and the baseline grow far less (see the scenario 6 table's RSS rows). `len(members())` ends at 0 in every batch run, so the batch's member state doesn't grow. What does grow wasn't investigated.
- **The warm pool, not pacing, limits rolling acquire.** In every scenario 6 variant, batch and baseline alike, the warm pool's Ready count hits 0 during the run. That's why acquire p90 and p99 are tens of seconds while p50 is under a second: those acquires wait for a cold pod.
- **Async renewals run late during create_rps=1000 fills.** In 2b async at N = 10,000, two of three runs had a renewal gap over the 2 s interval, with renewal p99 over a second, and no connection was discarded. 2c async, with a smaller pool, didn't. The driver used about 0.8 cores during these fills, so a busy event loop is the likely cause rather than the pool. That's a likely cause, not a measured one.

- **With `lease_duration=6`, a detached batch can be re-attached for only 1 s.** `2b-n10000-pool102-sync-run2` raised `BatchLeaseExpiredError: batch 'bgm2bx24n32m' Lease is missing or stale in namespace 'batch-bench'` from `get_batch()` right after `detach()`. `detach()` without `grace` keeps the Lease valid for the Lease duration (6 s). `get_batch()` treats a Lease as stale once `now > renewTime + duration - CLOCK_SKEW_MARGIN` (5 s), and it takes `now` after listing the batch's claims. That leaves 1 s for the Lease read and the claim list together. Run 1's 10,000-claim list took 0.69 s and attached; run 2's took longer and didn't. Since a Lease duration must exceed the 5 s margin, 6 s is the shortest allowed, and it gives the narrowest window.

- **connect() skips the Sandbox read only for a member's first command.** In `in-cluster-pod-ip` mode, `CommandExecutor` calls `connector.connect()` before every command (`command_executor.py`: "A direct Pod IP connection refreshes its target for every command"). `SandboxdInClusterStrategy.connect()` resolves the pod IP each time. `Sandbox._resolve_pod_ip()` uses the pod IP that `batch.connect()` seeded only once, then falls back to `get_pod_ip()`, which is a Sandbox GET. The gRPC channel is reused, so connections stay at one per member, but every command after a member's first makes one Sandbox GET. Scenario 4's per-round GET counts measure this.

### 2026-10 rerun notes

- **Between-run cleanup.** wait_clean deleted leftover pods by name, 200 per `kubectl delete`, from one listing, so after the 1a-n5000 rerun it spent about 28 minutes on pods the garbage collector had already removed (the laptop also slept during it). It now deletes unscheduled pods with one `--field-selector spec.nodeName=` request (warm pods are always on the node) and lists again after each 200-name batch. No run measures this cleanup, and no timed run was running during the stall.
- **A wrong supersede, undone.** The first `bench.py errored --supersede` scanned every result and moved `2b-n10000-pool102-sync-run2.json`, the known `get_batch()` crash kept above. It was moved back unchanged before anything reran it, and `errored` now looks only at the rerun's labels.
- **memdiag method.** Each point runs `gc.collect()` first, counts objects by type before the snapshot, and keeps the snapshot on disk, since a snapshot held in memory is one tuple per trace and would show up as growth at the next point. Traces with a frame in the probe's own `mem_point` are left out of the top 20.
