## Most important findings (first report)

1. **#42 is met.** Its approved goal was to remove the N Sandbox GETs at the fan-out: round 1 makes 0 GETs against the baseline's 300. The GET on every later command is existing sandboxd pod-IP behavior: the connector re-resolves the pod IP before each command, and the baseline makes the same number (2,700 vs 2,700 over rounds 2–10). Rounds 2–10 also open 17–20 new TCP connections in the batch runs (`4-batch-sync`, `4-batch-async`) against 0 for the baseline. The likely cause is those GETs overflowing the batch's 22-connection API pool; that's inferred, not measured. Pod-IP connections are reused as intended: 300 for 300 members.
2. **#41: the + 2 is needed.** With pool 100 and the check off, the sync client discarded a connection in 6 of 6 runs; with 102 it discarded none. Async never discarded, but at 1,000 creates/s its renewals ran late. The likely cause is a busy event loop (about 0.8 cores), not the pool.
3. **#47: the batch is much cheaper but not always faster.** Cold, it costs 4.9x fewer requests, 101x fewer watches and 60x fewer connections, and reaches all Ready in the same time. On warm pools, the default 50/s pacing makes it slower to reach all Ready than the baseline: 2.2x slower in 3b and 3.3x slower in 3c.
4. **#35 pagination:** the list time is fine (longest 0.48 s), but get_batch's attach adds more than 100 MB of RSS in the sync shell from N=5,000.
5. **Async rolling RSS grew 92 → 653 MB** over 1,000 rollouts, while `members()` stayed at 0. The 2026-10 rerun's memdiag looks into it (see Rerun 2026-10).

What the Problems section adds:

- **Attach window:** with `lease_duration=6`, `get_batch()` after `detach()` has only a 1 s window, so a 10,000-claim attach can raise `BatchLeaseExpiredError`.
- **Garbage-collector backlog:** after 10,000-claim runs, kind's garbage collector falls behind. The suite now waits for it between runs. One kept run, `4-batch-sync-run1`, has Ready and cleanup times that aren't comparable with the others', and one interrupted attempt was run again.
- **Planning bug:** scenario 2 first ran at N=5,000 by mistake. Those runs are kept as extra data.
- **Admission patch:** under kind v0.31, deploy-kind's admission patch silently doesn't apply.
- **Driver Role:** the README's driver Role lacks `get` on `sandboxes`, which pod-IP mode needs.

**Open questions:** whether these numbers settle each planned optimization, and whether to investigate the async RSS growth and the per-command Sandbox GET in pod-IP mode.

### Setup notes and deviations

- **Cluster.** One kind node, created from `kind-config.yaml`, not `make deploy-kind`. It uses deploy-kind's config plus kubelet `maxPods: 400`, a `/22` per-node pod CIDR (the default `/24` caps a node near 254 pods), and a mount of the repo at `/src` for the driver pod. The controller and sandboxd images were built and loaded with `dev/tools/push-images`, and deployed with `dev/tools/deploy-to-kube --extensions`, the two steps `deploy-kind` runs after creating the cluster.
- **deploy-kind's admission patch doesn't apply under kind v0.31.** `create-kind-cluster` patches `kubeadm.k8s.io/v1beta4`, but kind v0.31 renders `v1beta3`, so the patch matches nothing and is dropped without an error. In clusters made by `make deploy-kind` on this machine, the apiserver runs `--enable-admission-plugins=NodeRestriction` only, without `OwnerReferencesPermissionEnforcement`. This cluster's config uses `v1beta3`, so here the plugin is on, and the batch's ownerReferences are checked against the driver's Role.
- **Other kind clusters stopped.** Four other kind clusters on this machine were stopped for the whole benchmark, so they don't share the VM's CPU.
- **Node restart.** The VM restarted once between the earlier fill runs and this suite. All containers exited with 137 at the same moment, and the batch-bench node was started again. The imported 1a runs finished before that.

### Problems found

- **The async driver's RSS grows during rolling acquire.** In 6c (async, 1,000 rollouts), the RSS samples rise several times over from start to end, while the sync batch (6a, 6b) and the baseline grow far less (see the scenario 6 table's RSS rows). `len(members())` ends at 0 in every batch run, so the batch's member state doesn't grow. What does grow wasn't investigated.
- **The warm pool, not pacing, limits rolling acquire.** In every scenario 6 variant, batch and baseline alike, the warm pool's Ready count hits 0 during the run. That's why acquire p90 and p99 are tens of seconds while p50 is under a second: those acquires wait for a cold pod.
- **Async renewals run late during create_rps=1000 fills.** In 2b async at N = 10,000, two of three runs had a renewal gap over the 2 s interval, with renewal p99 over a second, and no connection was discarded. 2c async, with a smaller pool, didn't. The driver used about 0.8 cores during these fills, so a busy event loop is the likely cause rather than the pool. That's a likely cause, not a measured one.

- **With `lease_duration=6`, a detached batch can be re-attached for only 1 s.** `2b-n10000-pool102-sync-run2` raised `BatchLeaseExpiredError: batch 'bgm2bx24n32m' Lease is missing or stale in namespace 'batch-bench'` from `get_batch()` right after `detach()`. `detach()` without `grace` keeps the Lease valid for the Lease duration (6 s). `get_batch()` treats a Lease as stale once `now > renewTime + duration - CLOCK_SKEW_MARGIN` (5 s), and it takes `now` after listing the batch's claims. That leaves 1 s for the Lease read and the claim list together. Run 1's 10,000-claim list took 0.69 s and attached; run 2's took longer and didn't. Since a Lease duration must exceed the 5 s margin, 6 s is the shortest allowed, and it gives the narrowest window.

- **connect() skips the Sandbox read only for a member's first command.** In `in-cluster-pod-ip` mode, `CommandExecutor` calls `connector.connect()` before every command (`command_executor.py`: "A direct Pod IP connection refreshes its target for every command"). `SandboxdInClusterStrategy.connect()` resolves the pod IP each time. `Sandbox._resolve_pod_ip()` uses the pod IP that `batch.connect()` seeded only once, then falls back to `get_pod_ip()`, which is a Sandbox GET. The gRPC channel is reused, so connections stay at one per member, but every command after a member's first makes one Sandbox GET. Scenario 4's per-round GET counts measure this.
