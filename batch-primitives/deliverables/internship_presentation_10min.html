Slide 3 of 9 • SandboxBatch Architecture (Zero New CRDs) 1:55 - 3:10 (75s)
SandboxBatch collapses N claim lifecycles onto one shared watch, one Lease, and zero-GET connect()
Lifecycle Operation (N = 1,000) Legacy per_claim SandboxBatch Verified Architectural Gain
Readiness Watches 1,000 watch streams 1 label-scoped stream 11.1x fewer sockets (44 flat vs 488 held sockets)
connect() Metadata Reads 1,000 - 2,000 GETs 0 GETs (watch seeds podIPs) 1.02 - 1.25 vs 4.00 claim-path API requests/sandbox
Normal Bulk release() 1,000 DELETEs (35.93s) 1 deletecollection + 1 Lease DELETE 500x fewer calls, 1.10s best (32.5x faster)
  • Zero Server-Side Changes: Works immediately against unmodified v1beta1 clusters using standard SandboxClaims and one coordination.k8s.io/v1 Lease.
  • Warm-Aware Creation Pacing: Prechecks seed status.readyReplicas warm credit so warm claims dispatch immediately up to max_in_flight, falling back to create_rps on cold-start watch signals.
  • Zero-GET Connectivity: connect(member) seeds the pod IP directly from the shared claim watch and automatically closes cached connections if a pod is lost or replaced.
Slide 4 of 9 • Four Workload Patterns & Cross-SDK Parity 3:10 - 4:20 (70s)
Three initial-fill modes plus dynamic acquire() cover synchronous RL, multi-suite eval, and rolling queues across Python and Go
Consumption Pattern SDK Method Best-Fit Workload & Runtime Semantics
1. Joint Cohort Barrier wait_for_quorum() Sync Multi-Pool RL: Blocks until every group reaches min_ready, fails fast via QuorumUnreachableError, and trims spares via release_not_ready().
2. Per-Group Cohort Stream group_outcomes() Multi-Suite Eval: Yields each GroupOutcome as its own pool hits min_ready; an unhealthy pool never stalls healthy pools.
3. Pure Streaming events() 1:1 Task Sweeps: Emits MEMBER_READY / FAILED / LOST immediately with zero barrier; supports concurrent work-stealing loops.
4. Dynamic Rolling Pool acquire(pool, *, pod_annotations=...) Async RL & SandboxFleet: Starts at size=0 and adds/releases Ready sandboxes on demand over one shared watch + per-pod snapshot metadata.

Python SDK (Shipped: Sync & Async Parity)

SandboxBatch and AsyncSandboxBatch expose identical methods, frozen Pydantic models, except BatchError boundaries, and detach(grace) / get_batch() handoffs.

Go SDK (Rev 3.2 Prototyped & Wire-Compatible)

ClaimBatch(ctx, groups, ns, ...BatchOption), Go 1.23 iter.Seq2[T, error] iterators, borrowed *Sandbox handles, auto QPS=-1, and live Python <-> Go handoff on kind.

  • One Primitive, Four Dispatch Shapes: Supports over-requested synchronous quorums (size > min_ready), independent pool cohorts, zero-barrier streaming, and dynamic acquire() with per-pod annotations.
  • Python Sync & Async Parity: Identical public signatures, frozen Pydantic models, and error boundaries across threaded and asyncio applications.
  • Prototyped Go SDK Alignment: Golden-tested across 294 wire cases and 33 state-machine traces with live cross-language Python <-> Go batch handoffs on kind.
Slide 5 of 9 • Crash-Safe Distributed Ownership & Incarnation Fencing 4:20 - 5:35 (75s)
Lease ownerReferences, batch-lease-uid fencing, and a full LeaseDuration reaper wait prevent both leaked and mis-deleted sandboxes
Multi-Process Race Scenario Failure Without Incarnation Fencing Shipped Protocol Invariant (#2154, #2188)
Stalled Driver + Reused batch_id Old paused driver wakes up after reap and runs deletecollection on batch-id, wiping the new incarnation's claims. Every claim carries agents.x-k8s.io/batch-lease-uid: <lease.uid>; post-Lease watches & deletes select (batch-id, batch-lease-uid) and verify Lease uid / leaseTransitions.
Slow Renewal Transit vs. Reaper Delete Holder stamps renewTime before transit and self-fences at sent_at + D; early reap could race one final create. Holder self-fences monotonically at sent_at + D; batch_reaper observes now > renewTime + D + margin, waits full D, then deletes Lease with resourceVersion precondition.
  • Three-Layer Cleanup Defense: Combines O(1) release(), Lease-backed batch_reaper + Kubernetes cascading GC, and per-claim shutdownTime controller TTLs.
  • Least-Privilege Reaper RBAC: Because every claim carries an ownerReference to its Lease, batch_reaper needs only get, list, and delete on leases and never touches claims.
  • Zero-Orphan Late-Commit Closure: Even if an in-flight POST commits in kube-apiserver after Lease deletion during a lost cancellation, Kubernetes GC sweeps it in 19 - 28 ms.

3 Systems Lessons from 148,544 GKE Rollouts

1. Watch Fan-Out Dominates Tail Latency: Collapsing N watches into 1 cut claim p99 7.24x (139.66s -> 19.30s) even when 0 HTTP 429s occurred.

2. Insulate Foreground Binding from Pool Refills: Bounding --sandbox-warm-pool-concurrent-workers + max-refill-rate=100 + 30-share APF split prevents 155x workload-low queue spikes.

3. Benchmark Reset Cost vs. Fresh Warm Pods: Fresh SandboxBatch warm adoption (87.40s) beats in-place gVisor git restore (429.24s) by 4.91x with stronger episode isolation.

GKE 3-Lane APF Architecture (<= 30 Shares Cap)

agent-sandbox-critical (20 non-lendable shares for controller reconciles), agent-sandbox-bulk (10 shares for in-cluster drivers), and global-default for leader-election Lease renewals.

Node & Pod Throughput Levers

terminationGracePeriodSeconds: 0 removes 30s sleep infinity maxPods walls between steps; 600 GB Secondary Boot Disk (CONTAINER_IMAGE_CACHE) cuts median exec to 370 ms.

  • Why Self-Hosted APF Manifests Fail on GKE: flowcontrol-guardrails blocks mapping user SAs to exempt and caps custom PriorityLevelConfiguration shares at <= 30.
  • GKE 3-Lane APF Split: Isolates urgent foreground claim binding from high-volume warm-pool pod refill traffic inside GKE's managed guardrails.
  • Node & Pod Levers: Combines instant pod termination with pre-cached Secondary Boot Disk container layers for cold and multi-image R2E-Gym sweeps.
