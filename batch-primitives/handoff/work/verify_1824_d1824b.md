# Verification of 12/N round 3 restack (PR2 221a6c41, PR5 3795c13d, top eb5e9921)

Line refs: sync = sandbox_batch.py, async = async_sandbox_batch.py, at PR2 221a6c41 unless marked.

## Problems, ranked
I found no break of R1, R2 or R3 inside the approved scope.

1. MEDIUM, inferred, outside the approved scope. PR5's member deletes aren't serialized with detach(). This is the same race as N1, but for release_member, release_group and release_not_ready (sync@3795c13d:609-615, 638-650, 674-688). They pass `_check_active` (:417-419) and then delete. `_check_lease_held` (:421-426) checks err() only, not `_lease_released` or a detach in progress. Path: thread A runs release_group(g) and passes `_check_active`. Thread B runs detach(), which completes, and client C attaches. A's deletecollection rounds then delete group g's claims, which now belong to C. Round 2 decision 2 only settled the err() guard, and N1 didn't consider these methods. Smallest fix: take `self._lifecycle_lock` around the delete phase of the three methods, so detach() waits like it does for release(). An alternative is to refuse detach() while a member delete is running. A flag check in hold doesn't fix it: it's still check-then-act.
2. LOW, verified. A test now covers an interleaving that can't happen. `test_release_during_detach_keeps_the_detach_grace` (sync test :994-1010, async test :1047-1063) has release() clear `_detach_grace` during detach()'s write. release() now blocks on the lifecycle lock during that write, so this can't happen in async at all. In sync it happens only on a same-thread re-entry, and that re-entered release() would delete the whole batch. The comment "release() clears the stored grace, which a detach() that is already writing must not pick up" is stale. The real contract is the code comment at sync :587-588 (another detach() changes `_detach_grace`). Fix: inject `_detach_grace = 99`, as a second detach(grace=99) would, and rename the test and reword its comment. It still kills the "use `self._detach_grace` in the write" mutation.
3. LOW, verified. The 409 comments name a cause that is now serialized. See sync :625-628, async :630-633 (top: sync :1172-1175), and the 11/N test comment at sync test :956-957 and async test :1009-1010. "A concurrent detach() of this handle leaves it released": detach()'s Lease I/O is now under the lifecycle lock. What still produces "released after a 409" is an earlier detach() whose write timed out and landed late, or a same-thread re-entry in sync. Fix: reword both shells and both tests.
4. LOW, inferred. A same-thread release() inside detach() (sync, from a signal handler) goes through the RLock. It deletes the batch while the outer detach() then returns success. The spec analyzed only detach() inside release(), which is refused by the started check. The spec says re-entry "goes through, as today". Leave it, or document it.
5. LOW, verified by grep. The approved deviation has no test: async detach() after close() raises BatchError. Fix: add `with self.assertRaises(BatchError): await handle.detach()` to `test_close_stops_tracked_batches_and_closes_their_connections`.
6. NIT. `last_lease: Any` could be `V1Lease`. Both files import it, and `self._lease` is typed V1Lease. Also, async detach() has an extra blank line before `_unregister_batch` (async :644) that sync doesn't have (cosmetic).
7. PRE-EXISTING, not this change. Async close() / `_stop_batches` doesn't take `_lifecycle_lock`. So close() during a release() closes the k8s helper under it and unregisters the handle, and a release() after close() still runs.
