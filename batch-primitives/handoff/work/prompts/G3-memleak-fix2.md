## PR 1. Registry: `terminate()` removes its own entry
Branch `fix/python-sdk-release-terminated-handles` (yours, never opened). `timeout 60 git fetch upstream`, rebase it onto the fresh `upstream/main`, and replace the lazy prune with the hook (amend into the single commit; force-with-lease your own branch).
- Mechanism (from the audit, re-verify): a class attribute on both handle classes, `_on_terminated: Callable[[Self], None] | None = None` (use the typing form the file already uses). The client sets `sandbox._on_terminated = self._untrack` at every place it builds or inserts a handle (`create_sandbox` and `get_sandbox`, both shells). `terminate()` calls it after the delete succeeds and before it clears `claim_name`. `_untrack(handle)` removes the dict entry only if the entry is still that same handle (`is`). A private attribute, not a constructor argument, so third-party subclasses with a fixed `__init__` keep working. Keep the existing pop in `delete_sandbox`: removing it would change behavior for subclasses whose `terminate()` skips `super()` and break the existing sync test `test_sandboxclient.py:185-192` (a mocked terminate never calls the hook). Note it in the PR body as intentional.
- Concurrency: no new lock. The sync client locks nothing today, and the `is`-guarded removal is already safer than today's unconditional pop; say so in one sentence in the PR body. Async needs no lock (no await between the check and the delete).
- Tests, both shells, one owning test per contract (three contracts), each mutation-checked: terminate removes the entry (mutation: remove the hook call); a failed delete keeps the entry so exit cleanup still retries (mutation: move the call before the delete); terminating a stale handle does not remove a newer handle for the same claim (mutation: drop the `is` check). `close_connection()` keeping the entry is existing behavior PR 1 does not touch; point to an existing test if one covers it, do not add one. Close any extra handle a test opens.
- Commit message leads with the problem (every terminated handle kept, about 0.7 MiB each async) and says the change bounds the registry; it does not claim memory is flat (PR 2 covers that).

## PR 3. Exit hook keeps closed clients alive (research and options first; implement only after Brian picks)
New branch `fix/python-sdk-release-client-exit-hook`, new worktree off a freshly fetched `upstream/main`. Facts from the coordinator's reviewer at `f83f2d87` (re-verify):
- The async client registers `atexit.register(self._atexit_cleanup)` (~`async_sandbox_client.py:203`); the hook holds the client and everything it owns until exit, even after `close()`.
- Async `close()` is not final: `AsyncK8sHelper.close()` resets `_api_client`/`_initialized` so the client lazily re-initializes and can be reused (`async_k8s_helper.py` ~:561-570), and `close()` deliberately keeps handles whose `close_connection()` failed "so a later call can retry" (~:219-232); today the exit hook retries those and also covers sandboxes created after `close()`. So an unconditional `atexit.unregister` in `close()` drops exit cleanup for both cases.
- The sync client registers `atexit.register(self._delete_automatic_sandboxes)` (~`sandbox_client.py:106`), never unregisters it, and has no `close()`, only `__exit__` (~:111-118).
Do: verify these; then write the options with costs in the results file as a decision for Brian, not "smallest wins". At least: (a) unregister in `close()` only when the registry is empty afterwards (loses cleanup for sandboxes created after `close()` unless re-registered on the next track, which adds state); (b) a weak-reference hook (a module-level function holding a `weakref` to the client; cost: a dropped, never-closed client loses exit cleanup); (c) leave it and document that clients should be reused, not created per task. For sync, describe the same problem in issue 4 and list "unregister in `__exit__`" with its cost (behavior change if the client is reused after the `with` block) as a separate option; do not implement sync.
