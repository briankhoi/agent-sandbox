## Goal
Find out whether the async per-claim baseline's native memory growth is allocator fragmentation or a leak. Earlier measurement (verified in `results/6v2-baseline-async-run1.json` on `origin/bench/batch-claim`): the async baseline driver's RSS rose steadily from 93 MB to 514 MB over 600 rollouts in 155 s (about +27 MB per 10 s, no plateau); the batch async variant went 94 to 278 MB (peak 282); Python-traced memory (tracemalloc, measured in the tip memdiag run, not in the baseline) stayed flat near 11 MB. So the growth is probably native (inferred for the baseline), and it exists without any batch code.

Run the same baseline loop for about 10 minutes, once as shipped and once with `MALLOC_ARENA_MAX=2` in the driver's environment. If the growth flattens with `MALLOC_ARENA_MAX=2`, it is glibc arena fragmentation; if it keeps rising, it is either main-arena fragmentation or live growth (a leak or unbounded cache), which the malloc probe (`mallinfo2` and `malloc_trim`) separates, and memray then locates. Deliver the two RSS curves (data and a plot), a verdict with evidence, and a drafted upstream issue text for Brian to file. This does not touch the PR stack.

## Verdict rule (fixed before looking at data; do not change it afterwards)
The RSS series covers the whole driver run, including imports, setup and close (sampler start B:853, stop B:740), and has no rollout counts. So record the rolling phase's start and end on the sampler's clock (edit 3b) and fit only inside that window. Slope = least-squares MB/s over the second half of the rolling window; MB per 100 rollouts = slope_MB_per_s / (rollouts / rolling_wall_s) x 100 (derived; label it so). Final RSS = last sample inside the rolling window.
- **Arena fragmentation**: the arena2 run's slope is at most 20% of the default run's, and its final RSS is at most 60% of the default run's.
- **Not arena fragmentation**: the arena2 run's slope is at least 60% of the default run's. This does NOT prove a leak: `MALLOC_ARENA_MAX` limits only the per-thread arenas, and the event loop allocates mostly in the main arena. Decide with the malloc probe below.
- Anything else: **inconclusive**.
Malloc probe (both runs, edit 3b): at the end of the rolling phase, before close, record RSS, then glibc `mallinfo2()` via ctypes (`uordblks` = bytes in use, `fordblks` = free bytes held), then call `malloc_trim(0)` and record RSS and `mallinfo2()` again. Reading: in-use bytes (`uordblks`) growing to most of RSS means live allocations (a leak or an unbounded cache, run step 8); a large free share that `malloc_trim` returns to the OS means fragmentation (main arena included), even if arena2 did not flatten. State which reading the numbers support.
Also report both runs' rollouts/min, so a slower run is not mistaken for less growth (slope per rollout handles this, but state it).
