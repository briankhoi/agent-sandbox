## Q2. Preserving `#2087` Static `atexit` Hooks Alongside Batch Exit Cleanup

### Decision: Confirm Option 2A

- **Recommendation:** Pass the client's in-place batch containers into the static `functools.partial` hooks on both clients, and update the existing unit test call sites rather than adding default `None` parameters in production.
- **Alternatives considered:**
  - *Option 2B (`weakref.WeakMethod` on `_release_batches` or skipping batch cleanup after client GC):* Fails to clean up if a caller drops its local `client` reference while relying on `cleanup=True` at process exit, or keeps `client` alive via `batch._client` anyway while a batch is active. Rejected.

### Lifecycle & Reference-Graph Verification (`verified` against `bcf5d4a0` and `f8b388a3`)

1. **Zero reference retention after cleanup:**
   - Neither client ever rebinds `_active_connection_sandboxes`, `_explicit_claims`, `_active_batches`, `_closing_batches`, or `_batches_lock` (`f8b388a3:sandbox_client.py:107-115`, `async_sandbox_client.py:203-210`, `verified`).
   - Once every batch on a client finishes `release()`, `detach()`, `delete_all()`, or `await client.close()`, `_unregister_batch` and `_track_closing` empty both `_active_batches` and `_closing_batches` (`f8b388a3:sandbox_client.py:513-531`, `async_sandbox_client.py:677-693`, `verified`). All four containers held by `functools.partial` are empty, so `del batch; del client` frees the client immediately by refcounting even with `gc.disable()`.
   - While a batch remains active (or sits in `_closing_batches` after a failed connection close per `10/N` `#2049`), `_active_batches` / `_closing_batches` intentionally retains `batch` (and `batch._client`) so exit cleanup still releases claimed batches, detaches `get_batch`-attached batches (`12/N`), and closes lingering port-forward subprocesses (`f8b388a3:sandbox_client.py:603-638`, `async_sandbox_client.py:798-863`, `verified`).

## Q3. Forwarding `#2132` (`_default_ssl_context`) and `#2085` (`_on_terminated`) in `connect()`

### Decision: Confirm Option 3A, with Unconditional `_default_ssl_context` Assignment

1. **`_default_ssl_context` in `AsyncSandboxBatch.connect()` (`#2132` `9f7999b3`): assign unconditionally (`verified`):**
   - **Correction to Option 3A's snippet (`working_rules.md:55,57`):** Do **not** add `if self._client._default_ssl_context is not None:` in `AsyncSandboxBatch.connect()`, and do **not** set `self.mock_client._default_ssl_context = None` in `TestConnect.setUp`.
   - **Reason:** Unlike `file_config: SandboxFileConfig | None = None` (which is optional and passed as a constructor kwarg that custom `sandbox_class` subclasses might not accept), `AsyncSandboxClient.__init__` initializes `self._default_ssl_context = _DefaultSSLContext()` (`bcf5d4a0:async_sandbox_client.py:202`, `verified`) and `close()` resets `self._default_ssl_context = _DefaultSSLContext()` (`line 241`, `verified`). It is **never `None`**, and `AsyncSandboxConnector._default_ssl_context` has type `Callable[[], ssl.SSLContext]` (not `Optional`, `bcf5d4a0:async_connector.py:242`, `verified`).
   - `AsyncSandboxClient._attach_handle` sets `sandbox.connector._default_ssl_context = self._default_ssl_context` unconditionally (`bcf5d4a0:async_sandbox_client.py:246`, `verified`). Doing the exact same 1-line unconditional assignment in `AsyncSandboxBatch.connect()` right next to `sandbox._seeded_pod_ip = pod_ip` (`f8b388a3:async_sandbox_batch.py:553`) works on every real `AsyncSandbox` subclass and on `MagicMock` in `TestConnect` alike, passes `mypy --strict`, and avoids adding a branch to production code for a test double (`working_rules.md:55`).
   - *(Sync `SandboxBatch.connect()` needs only `file_config` forwarding, because sync `SandboxConnector` does not use `_DefaultSSLContext`, `verified` at `bcf5d4a0:connector.py`.)*

2. **`_on_terminated` on batch-connected handles (`#2085` `7b1a9fbc`): leave unset (`None`) (`verified`):**
   - **Alternatives considered:**
     - *Option 3A (leave `sandbox._on_terminated = None`):* Zero added code or lock coupling; bounded memory; fails closed if a caller misuses `sandbox.terminate()`.
     - *Alternative (bind `sandbox._on_terminated` to pop `batch._connected[member.claim_name]`):* Rejected for both minimal-code and **pod-IP safety** reasons (`verified`):
       1. **Memory is already bounded and cycle-free:** `#2085` fixed unbounded growth in `client._active_connection_sandboxes` across the lifetime of a client. Batch handles never enter `client._active_connection_sandboxes`; `batch._connected` is bounded by the batch's members, `sandbox.terminate()` calls `close_connection()` which immediately breaks the `sandbox <-> connector` cycle via `#2086` (`bcf5d4a0:sandbox.py:271,293-305`, `verified`), and the batch watch evicts `(sandbox, pod_ip)` from `batch._connected` as soon as it sees `deletionTimestamp` / `DELETED` (`f8b388a3:sandbox_batch.py:1185-1197`, `verified`).
       2. **Pod-IP safety hazard if `_on_terminated` evicted `batch._connected` early (`verified`):** Batch member deletion belongs to `batch.release_member(member)` (`f8b388a3:sandbox_batch.py:928`, `d9d5c258:examples/agent-sandbox-rl/agent_sandbox_rl/handles.py:612-614`), which atomically marks the member released in `batch._state` under `batch._lock` before deleting the claim. If a caller instead called `sandbox.terminate()` directly and `_on_terminated` popped `batch._connected[member.claim_name]` *before* the batch watch observed the claim deletion, `batch._state.get_member(member.claim_name)` would still report `MemberState.READY` while `cached` became `None` (`f8b388a3:sandbox_batch.py:528-556`). A second `batch.connect(member)` in that race window would construct a **brand-new live `Sandbox` seeded with the deleted claim's old `pod_ip`**. Leaving `(closed_sandbox, pod_ip)` in `batch._connected` until the watch marks the member `LOST` returns the already-closed handle (`is_active == False`), failing closed without opening a new connection to a terminating pod IP.
