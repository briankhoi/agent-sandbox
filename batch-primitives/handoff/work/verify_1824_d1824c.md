# Verification of 12/N and 15/N `review/d1824c/*` (PR 2 `93c1711a`, PR 5 `87920a45`, top `bc136925`)

Base: `7cfe8484` (`upstream/feature/batch-claim`). Line references at `bc136925` (`review/d1824c/feat/batch-7a-create-path`) unless marked.

## Rules checked
- **R1 (PR 2 sync `detach()` same-thread re-entry):** If `release()` runs on the same thread inside `SandboxBatch.detach()` (before, during, or after `detach()`'s Lease read or write, whether that `release()` succeeds or fails), `detach()` raises `BatchError`, never overwrites the Lease with `holder_identity = None`, and never sets `_lease_released = True` or unregisters a failed `release()`. A same-thread `detach()` inside `detach()` returns cleanly without hanging, even if the outer request fails after the inner `detach()` released the Lease.
- **R2 (PR 5 member and group delete serialization):** `release_member`, `release_not_ready`, and `release_group` (sync and async) hold `_lifecycle_lock` around their delete phase and check `_lease_released` and `err()` in `_check_lease_held`, so they never send claim deletes concurrently with `detach()`'s Lease release I/O or after the Lease leaves this handle.

## What was tightened after the fresh verifier run
1. **PR 2 (`sandbox_batch.py` `detach()`):** Wrapped the Lease read and write block inside `with self._lifecycle_lock:` in `try ... except Exception: with self._lock: if self._detach_done(): return; raise`, and checked `if self._detach_done(): return` before `replace_batch_lease` and before `self._lease_released = True`. That closes both verifier edge cases in PR 2 (an error from `read_batch_lease` or a transport error after same-thread `release()`, and an outer error after a succeeded inner same-thread `detach()`).
2. **PR 5 (`sandbox_batch.py`, `async_sandbox_batch.py`):** Kept `_check_lease_held` to `if self._lease_released:` (plus `self._state.error()`), dropping the redundant `or self._release_started()` branch (`release()` already holds `_lifecycle_lock` for its whole run and sets `_lease_released = True` on completion or `BatchInUseError`, and keeps the Lease held on transient failure) and leaving `_delete_released_create` untouched. Updated the `_lifecycle_lock` comment to include member and group claim deletes.

## Separate findings in higher PRs (non-blocking for 12/N `#1824`)
1. **PR 6 (16/N `#1991`) `_drop_acquired()` and `may_exist` in `acquire()` (`sandbox_batch.py:684, 809-820`, `async_sandbox_batch.py:695, 829-840`):**
   - `_drop_acquired()` calls `_delete_claim()` without `_lifecycle_lock`, so if `detach()` wakes a waiting `acquire()`, `_drop_acquired()` can send `delete_sandbox_claim` concurrently with `detach()`'s Lease release write (and logs a warning when `err()` or `detach()` caused `_check_lease_held()` to raise `BatchError`).
   - `may_exist` starts as `True` before `_stop_creating.wait` / `_wait_for_stop`, so if `detach()`, `release()`, or an interrupt aborts `acquire()` during its pacing wait before `_create_one()` runs, `_drop_acquired()` sends an unnecessary `delete_sandbox_claim` for a claim it never created.
2. **PR 5 (15/N `#1990`) Lease expiry if `detach()` blocks past Lease TTL behind a slow delete (`sandbox_batch.py:421-428, 1046-1049`):**
   - `detach()` stops `_renew_loop` before waiting on `_lifecycle_lock`. If an already-running multi-round `release_group()` or retrying `_delete_claim()` stalls longer than the remaining Lease duration while `detach()` waits on `_lifecycle_lock`, the Lease expires without `_renew_loop` setting `err()` (`get_batch` still rejects an expired Lease, so this only matters if the reaper deletes the Lease after `leaseDurationSeconds + 60s` and a caller reuses the same custom `batch_id` before the next delete round).
