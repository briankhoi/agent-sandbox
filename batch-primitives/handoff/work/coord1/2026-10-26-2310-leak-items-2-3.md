## The three issues and their PRs

### Issue A, fixed by PR 1: the client never forgets terminated sandboxes
- **Problem:** the client keeps every sandbox handle in a dict, the "registry" (`_active_connection_sandboxes`). The registry exists so `get_sandbox()` can reuse a handle and so cleanup at exit can delete sandboxes you forgot. `terminate()` deletes the sandbox in Kubernetes but never removes its handle from the registry. Each async handle holds about 0.7 MiB (an HTTP client with SSL state), so memory grows forever: 94 MB to 1.75 GB over 2,400 sandboxes (measured).
- **PR 1:** when the client creates a handle, it gives the handle a small hook, `_on_terminated`, set to the client's own method `_untrack`. `terminate()` calls the hook after the delete succeeds, and the hook removes the handle from the registry (only if the registry still holds that same handle). Both clients.

### Issue B, fixed by PR 2: a finished handle's memory is freed late
- **Problem:** a handle and its connection object point at each other (the handle gives the connection its methods to look up the pod address). Python cannot free two objects that point at each other right away; it waits for its occasional garbage-collection pass, which ignores the OpenSSL memory. So even after PR 1, memory climbs high before it is freed.
- **PR 2:** when a handle is closed for good, one small method cuts the connection's link back to the handle, so the memory is freed immediately. Async does it at the end of the connection's `close()`; sync does it in `Sandbox.close_connection()`.
- **Together** (measured by G): memory growth per 100 sandboxes went from 90.1 MB on main to 0.46 MB; in your "create 100, terminate all, create none" case, memory kept per sandbox went from 0.667 MB to 0.0001 MB.

### Issue 4, fixed by PR 3: closed clients are never freed
- **Problem:** each client registers a cleanup function to run at program exit, and that registration holds the client itself, so no client is ever freed until the program ends, even after `close()`. Small per client (about 1.4 to 22 KB, depending on the measure), so it matters only for programs that create many clients.
- **PR 3, option (e) (you approved):** register a plain function that holds only what the exit cleanup needs (the registry and a few settings), not the client. Exit cleanup behaves exactly as today, and the client itself can be freed.

## Item 2: does PR 1 clash with PR 3? Partly, yes, and there is a cleaner fix than the one-liner I proposed
PR 1's hook is the client's own method, and a method remembers its object. So every handle in the registry points back at its client. With PR 3 in place:
- PR 3's exit function holds the registry, the registry holds handles, and each handle's hook holds the client. So **any client that still has handles in its registry is kept alive until exit again**, which is what PR 3 is meant to stop. Examples: a client you dropped while its sandboxes were still running, or a client whose `close()` failed for some handle. (Inferred from how Python methods work and PR 1's code; not yet measured.)
- My earlier one-liner (clear the hook after `terminate()` uses it) only helps for handles that were already terminated. It does not cover live handles, so it is not enough. I was wrong to call it the fix, because I only considered terminated handles.

**Better fix (proposal):** make PR 1's hook point at the registry, not at the client. For example the hook is a small function bound to the registry dict (`functools.partial(_untrack, registry)` style) instead of the client's method. The behavior of PR 1 stays the same (terminate removes its own entry, only if it is still that handle), but no handle ever points at the client, so PR 1 and PR 3 cannot clash, and the one-liner is not needed. About the same number of lines as today.

How we would confirm it: G adds one test in PR 3 that a closed client is freed even while its registry still holds a handle, run with PR 1 and PR 3 together.

**Decision 2:** change PR 1's hook to point at the registry instead of the client (before you open PR 1)? Recommended: yes. Alternative: keep PR 1 as is and accept that clients with tracked handles stay alive until exit (PR 3 then helps only clients whose registry is empty).

## Item 3: will users hit the PR 2 sync change?
- **Who could hit it:** only code that keeps a handle's connection object (or an executor taken before closing) and keeps using it **after** `close_connection()`. Normal use does not: after `close_connection()`, `sandbox.commands` and `sandbox.files` are already set to `None` today, so `sandbox.commands.run(...)` after closing already fails with an error on main. And `terminate()` calls `close_connection()`, so this is about using a sandbox you already terminated or closed.
- **What they would see after PR 2:** in pod-tunnel mode the request fails with an error (no pod name to tunnel to); in in-cluster mode it silently falls back to the service DNS name, which may still work; in Gateway mode the extra header is gone, so the gateway may reject it. Today on main the sync connection quietly reconnects instead.
- **Is it common?** No. It needs code that holds on to internals after closing, and the async client already refuses all use after close today, so PR 2 moves sync closer to async rather than away. Not a supported pattern; no docs or examples do it (inferred; G and the checker found no such use in the repo).

**Decision 3:** accept this and add one sentence to PR 2's description? Recommended: yes. The clean fix (make sync `close()` final and refuse use after close, like async) is issue 5, a separate later change.
