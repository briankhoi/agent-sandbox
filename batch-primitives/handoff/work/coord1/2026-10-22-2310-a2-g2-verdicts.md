## G2 decision (memory leak)
**What the review found** (fresh `inherit` subagent, read the fix branch `2e02e420` on upstream main `840fdfde`, formed its own view before reading the task's note):
1. **The registry fix (a) is sound and minimal** (verified). It uses existing data (`claim_name is None`, set only after a successful delete), adds no state, has one helper with identical comments in both shells, and keeps claims that are closed but still exist (so exit cleanup still deletes them). Two nits for the follow-up: the commit and PR text should say it bounds the registry, not that it ends all growth; the async test should close the extra handle it opens.
2. **Why 0.36 MiB per sandbox still grows** (verified in code): each handle and its connector reference each other (the handle passes its own `get_pod_ip`, `get_pod_name` and `get_service_fqdn` methods into the connector, which stores them). So a dropped handle is freed only by Python's full cyclic GC, which runs on object counts and never sees the ~0.7 MiB of OpenSSL memory behind each connection. Expected shape is a sawtooth with a high peak, which matches the measured "drops" (inferred; the 2,400-rollout runs will confirm).
3. **The task's option (i), clear the callbacks at close in both shells, is safe only in async** (verified). The async `close()` is final. The sync `close()` is a reset: it runs mid-request on errors and the next request reconnects, so clearing callbacks there would quietly break Pod-IP routing after the first transient error. The sync handle measured only 0.058 MiB, so parity does not justify the risk.
4. The 0.36 MiB figure is not checkable yet: those results and scripts are not pushed. G3 pushes them.

**Recommendation:** keep (a) as its own PR (with the two nits fixed). Add a second small PR off upstream main that clears the callbacks in the three async `close()` methods only (about 5 lines, no type change), with one GC-off test that a closed, dropped handle is freed, and a sentence on why sync is left alone. Then measure three arms (main, main + (a), main + both) before claiming the fix. Two PRs because they are different mechanisms in different files, and the cycle also affects handles that are never in the registry (AGENTS.md: one concern per PR).
