## 1. Why `@staticmethod` and where `self` went (verified at `afae285e`)
- Before PR 3, `__init__` ran `atexit.register(self._atexit_cleanup)`. In Python, `self._atexit_cleanup` on a normal method creates a bound-method object with a hidden reference to `self` (the `AsyncSandboxClient`).
- Python's `atexit` module keeps every registered callback in a process-global list until the Python interpreter exits. Holding `self` in that list kept every `AsyncSandboxClient` alive until process exit, even after `await client.close()` and `del client`.
- Adding `@staticmethod` removes `self` completely (`async_sandbox_client.py:550-555`). `self._atexit_cleanup` now evaluates to the plain function with no pointer back to `self`, so Python frees the `AsyncSandboxClient` as soon as the caller drops it.

## 2. What the first two parameters are, and how they stay live (verified at `afae285e`)
`_atexit_cleanup` used to read three attributes off `self`. With `self` gone, it receives those three objects directly:
1. **`registry` (`self._active_connection_sandboxes`, `dict[tuple[str, str], T]`):** the live dict mapping `(namespace, claim_name)` to each tracked `AsyncSandbox` handle. `_atexit_cleanup` reads it at `async_sandbox_client.py:568-571` (`claims = list(registry.keys())`) to close local connections (`sandbox._close_for_atexit()`) and know which claims are still open at exit.
2. **`explicit_claims` (`self._explicit_claims`, `set[tuple[str, str]]`):** the live set of `(namespace, claim_name)` pairs that the caller attached to by explicit claim name (`get_sandbox(...)` or `create_sandbox(..., claim_name=...)`). `_atexit_cleanup` checks `if (ns, claim_name) in explicit_claims: continue` at `async_sandbox_client.py:604` so exit cleanup closes their local connection without deleting a pre-existing Kubernetes `SandboxClaim`.
3. **`injected_api_client` (`api_client`):** the optional `AsyncApiClient` passed to `__init__` (`async_sandbox_client.py:587-593`). Notice PR 3 also deletes `self._injected_api_client = api_client` from `__init__` because nothing else on the client ever read it.

Why passing `registry` and `explicit_claims` in `__init__` still sees sandboxes created later: in Python, `dict` and `set` are mutable containers passed by object reference. The client mutates `self._active_connection_sandboxes` and `self._explicit_claims` in place during `create_sandbox`, `get_sandbox`, `terminate`, and `close` and never rebinds them to new containers (`async_sandbox_client.py:197-199`). The `partial` holds references to those exact same `dict` and `set` objects, so at interpreter exit it sees their current contents without holding the client itself.

## 3. Why you didn't see a call site near `_atexit_cleanup` in the diff (verified at `afae285e`)
Two reasons:
1. **No method in `AsyncSandboxClient` ever calls `_atexit_cleanup(...)` directly.** `__aexit__`, `close()`, and `delete_all()` are `async def` methods that `await self._delete_automatic_sandboxes()` (`async_sandbox_client.py:220, :543`), whereas `_atexit_cleanup` is only for Python's synchronous `atexit` shutdown hook. (By contrast, sync `SandboxClient.__exit__` is synchronous, so `sandbox_client.py:124` does show a direct call `self._delete_automatic_sandboxes(self._active_connection_sandboxes, self._explicit_claims)`.)
2. **The updated registration site is 345 lines higher up in Hunk 1 (`async_sandbox_client.py:206-208`):**
   ```python
   atexit.register(functools.partial(
       self._atexit_cleanup, self._active_connection_sandboxes, self._explicit_claims, api_client
   ))
   ```
   `functools.partial` pre-binds those three arguments (`self._active_connection_sandboxes`, `self._explicit_claims`, `api_client`) and hands `atexit.register(...)` a zero-argument callable that Python invokes automatically when the process exits. (Direct calls in unit tests are updated further down in the same commit in `test_async_sandboxclient.py`.)
